# Intent Matching and Slot Filling

[← Back to README](README.md) · [RAG pipeline](rag-pipeline.md)

## Why two levels of filtering

Pure embedding similarity search isn't always reliable for short, noisy
support messages. That's why a two-stage scheme is used:

1. **Fast filter (embeddings).** The Vector Store returns top-K candidates
   by cosine similarity — cheap, but can be wrong on paraphrases.
2. **Precise classification (LLM + structured output).** The model picks a
   single `intent_id` from the top-K candidates (or `out_of_scope`), which
   is cheaper and more reliable than classifying against the entire topic
   set at once.

```
user message
   │
   ▼
embedding similarity search (top-3)
   │
   ▼
LLM structured classification (enum: top-3 intent_id + out_of_scope)
   │
   ▼
confirmed intent
```

## Example structure of one "allowed question"

```json
{
  "intent_id": "refund_status",
  "canonical_questions": [
    "Where is my refund?",
    "When will the refund money arrive?",
    "Refund status"
  ],
  "required_slots": ["order_id"],
  "knowledge_snippet": "Refunds are processed within 3-5 business days from the moment the request is confirmed.",
  "system_instruction": "Answer only about refund status, use order_id for personalization",
  "allowed": true,
  "answer_template": "For order {order_id}: the refund is processed within 3-5 days from confirmation.",
  "escalation_fallback": "If the status is unclear, please contact a human agent."
}
```

## Example structured output from the LLM classifier

```json
{
  "intent_id": "refund_status",
  "confidence": 0.93
}
```

If `confidence` is below the threshold, or `intent_id == "out_of_scope"`,
the request is considered outside the allowed topic set.

## Slot filling: collecting missing context

Once `intent_id` is confirmed, the system checks whether all
`required_slots` are already present in the dialogue state (Cassandra — see
[dialogue-state.md](dialogue-state.md); there is no Redis in this project):

```
required_slots = ["order_id"]
dialogue_state  = {}          → order_id is missing
                                → the bot asks a clarifying question,
                                  staying within the intent_id topic
```

The clarifying question is generated by the same LLM, but with a prompt
constrained to the topic: the model can't "drift" to another topic during
clarification, since `intent_id` is already fixed for the session.

## Dialogue state diagram for a single intent

```
NEW ──▶ SLOT_FILLING ──▶ READY_TO_ANSWER ──▶ ANSWERED ──▶ ESCALATED (guardrail rejected the answer)
  │
  └──▶ OUT_OF_SCOPE (no candidate intent matched, or confidence/whitelist check failed)
```

Matches the implemented `DialogueStatus` enum exactly — see [dialogue-state.md](dialogue-state.md) for
why there's no separate `INTENT_MATCHED` state (folded into the classify-then-slot-check step) and what
`ESCALATED` (added in Phase 2, for the output-side guardrail) means.
