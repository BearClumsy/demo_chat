# 2026-08-13

## Chat authorization hole

- A code review of the morning's doc-correction commit turned up a real bug rather than drift:
  `POST /api/chats/{chatId}/participants` took no authenticated principal at all, and `ChatService`
  did no caller check — so any authenticated user who knew (or guessed) a chat id could add
  *themselves* to it, then read its history and post into it. The chat id was the only secret.
- Fixed by routing `addParticipant` through the existing `getChatForParticipant()`, the same gate the
  message endpoints already used, so all `/{chatId}/**` operations now fail the same way (403
  non-participant, 404 unknown chat).
- Ordering is deliberate: the caller check runs **before** `validateParticipantIds`. Validating first
  would have let an outsider use the endpoint's error shape to probe which user ids exist.
- The caller's id is passed as its own parameter from `@AuthenticationPrincipal` rather than read from
  the request body — the body is attacker-controlled, so trusting it would reintroduce the hole.
- Test added for the outsider case, asserting not just the `AccessDeniedException` but that
  `userRepository.findAllById` is never reached (the probe path) and nothing is saved.
- [[Chat]] and [[User]] were rewritten in the same pass — both had gone stale at their 2026-07-13
  skeleton state, still claiming there was no send-message endpoint and no way to pass a real caller
  id. [[chat_history]] corrected too.

## Flyway: standalone migration tasks

- Added `:server:flywayMigrate` / `:server:flywayInfo`. The app already migrates on startup, so this is
  purely for applying or inspecting the schema *without* booting the app — a fresh database, or
  checking pending state.
- The real hazard is that Flyway is now configured in two places: Boot's `spring.flyway.schemas` and
  the `flyway {}` block in `modules/server/build.gradle`. If `schemas` diverges between them, each
  path builds its own `flyway_schema_history` table and re-runs the other's migrations. Same reason
  the plugin is pinned to 11.14.1 — the `flyway-core` version the Boot BOM resolves — so both paths
  run the same engine.
- `flyway-database-postgresql` and the JDBC driver had to go on the `buildscript` classpath, not the
  project's configurations: the plugin loads database plugins from the buildscript classloader, and
  without them the tasks fail with "No Flyway database plugin found to handle jdbc:postgresql://…".
- `cleanDisabled = true` — `flywayClean` drops every object in the schema and there is no reason to
  leave that one keystroke away.
- Defaults point at the local docker-compose Postgres; `-Pflyway.*` / `FLYWAY_*` override per
  environment. Wrapped as `make migrate` / `make migrate-info`, documented in `CLAUDE.md`, `README.md`
  and the gotchas list. See [[users]] — still the only migrated table.
- Follow-up the same evening: `schemas` was the one setting the block *didn't* let you override, while
  advertising an override story for all the others. Staging and prod resolve `spring.flyway.schemas`
  from `POSTGRES_SCHEMA`, so anyone migrating either environment by the documented recipe would have
  written `flyway_schema_history` into `demo_chat` and left the app to build a second one — precisely
  the divergence the block's own comment warns about. Now `findProperty('flyway.schemas') ?:
  System.getenv('FLYWAY_SCHEMAS') ?: 'demo_chat'`; the plugin already merged `FLYWAY_SCHEMAS` over the
  extension, so this mostly makes an existing escape hatch visible.
- Worth recording because it constrains future changes: `POSTGRES_SCHEMA` is effectively pinned.
  `V1__create_users_table.sql` hardcodes `demo_chat.users`, so any other value yields a schema the app
  can't read — and V1 can't be rewritten to fix that, since it's already applied everywhere and a
  changed checksum fails `flyway validate` on startup. Moving schemas needs a new migration.

## Local tooling & tests

- `make up/down/logs/nuke` hardcoded `docker compose`, which simply fails on setups that only have the
  standalone `docker-compose` binary and no CLI plugin (Colima without Docker Desktop). Now probed at
  use time; assigned with `=` rather than `:=` so only the compose targets pay for the probe, not
  every `make` invocation.
- `compileTestJava` was warning on a deprecated API: Testcontainers 2.0.5 relocated each database
  module into its own package, deprecating `org.testcontainers.containers.PostgreSQLContainer` for
  `org.testcontainers.postgresql.PostgreSQLContainer`. The replacement is no longer self-typed, so the
  `<?>` wildcard and diamond come off; every accessor the tests use is unchanged.
- **Supersedes the 2026-07-15 Ryuk workaround**: `TESTCONTAINERS_RYUK_DISABLED=true` is not needed.
  `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock` fixes the same mount failure with Ryuk
  left enabled — it points the bind at the socket path as the Lima VM sees it. Confirmed by a full
  green `make clean build`. The daemon endpoint now comes from a machine-level
  `~/.testcontainers.properties` instead of per-shell exports; the socket override stays an env var
  only because it has no properties-file key. Still not baked into the build — it's a Colima quirk,
  not a project setting (see [[running-locally]]).
