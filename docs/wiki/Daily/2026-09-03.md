# 2026-09-03

## Phase 3b: Kubernetes deploy layer (kubeadm on EC2) — lint-only skeleton

Pivoted the deploy target from **ECS Fargate** to **self-managed Kubernetes (kubeadm) on EC2**
behind the NGINX Ingress Controller, and wrote out the whole layer as reviewable, CI-linted,
never-applied code. New doc: [[kubernetes]].

### Terraform (`infra/terraform/`)

- **New modules**: `k8s-cluster` (control-plane + worker ASGs, internal API NLB with `/readyz`
  health check, node IAM with Bedrock invoke + ECR pull + cluster-autoscaler perms, KMS key, a
  deploy/snapshot S3 bucket, the `kubectl-apply` / `kubectl-rollback` SSM documents, SSM VPC
  endpoints, `user-data-{controlplane,worker}.sh.tftpl`), `alb-k8s` (internet ALB, `target_type =
  "instance"` on the ingress NodePort 30080, health check on NodePort 30254, 300 s idle +
  deregistration delay for SSE), `ecr` (two repos, scan-on-push, lifecycle), `github-oidc` (GitHub
  OIDC provider + deploy role: ECR push, `secretsmanager:GetSecretValue`, `ssm:SendCommand`
  scoped to the documents + `k8s-role=control-plane` instances).
- **`envs/{staging,prod}` rewired** — drop the `ecs_service` call, add `k8s_cluster` / `alb_k8s` /
  `ecr` / `github_oidc`. New TODO vars: `node_ami_id`, `admin_cidr`, `github_org`,
  `kubernetes_version`. Removed `server_image` / `desired_count` (unused → would trip
  `terraform_unused_declarations`). `task_secret_arns` grew a 4th key, **`CASSANDRA_USER`** —
  Amazon Keyspaces issues a username+password pair and it was missing from the ECS contract
  (flagged in [[2026-08-31]]).
- **`ecs-service`, `alb`, `bedrock-iam` retained** as lint-clean references (each has a README
  saying so); no env instantiates them. `tflint --recursive` still checks them; not gutted so
  `terraform_unused_declarations` stays quiet.
- Kubeadm bootstrap without a designated node: control-plane + worker user-data race on an SSM
  `init-lock` parameter written **without `--overwrite`**; the winner runs `kubeadm init
  --upload-certs` and publishes join commands to SSM SecureString; a systemd timer on each
  control-plane node refreshes the (24 h / 2 h) tokens every 6 h; a second timer snapshots etcd to
  S3. Worker join is gated by an ASG `EC2_INSTANCE_LAUNCHING` lifecycle hook.

## Offline profile: commit `11374d4`, then containerise Ollama and boot it for real

The committed `offline` profile (`11374d4`, activated `local,offline` via `make run-offline`) swaps
both `spring.ai.model.*` selectors to a local Ollama so the whole RAG pipeline — the two
structured-output stages included — runs with nothing from AWS. `make run` (Bedrock) can't even
start without credentials, because collection sizing calls the embedding model during context init.
Follow-on session work below. See [[roadmap]] Phase 3a, [[local-vs-aws]].

### Ollama in a container, not a host install

- `local/docker-compose.yml` gains an `ollama` service, gated behind a Compose
  **`profiles: ["offline"]`** so a plain `make up` (the Bedrock path) never starts it or eats the
  multi-GB model download. New `make up-offline` opts in; `down` / `nuke` also carry
  `--profile offline` so they stop the extra container; `make ollama-pull` now `exec`s into the
  container instead of calling a host binary.
- Model pull ended up **in the Makefile, synchronous** (see Race fix below), not a compose sidecar.
  `ollama-models` is a plain compose-managed volume — `make nuke` (`down -v`) wipes it like the
  other data volumes and the next `make up-offline` re-pulls (~5 GB), blocking until done.
- **Why not replace the native install outright**: on Apple Silicon a Linux container gets no
  Metal/GPU passthrough under Docker Desktop / Colima, so containerised Ollama is CPU-only and
  slower. Docker Model Runner *does* use the GPU but isn't a container and speaks the OpenAI API,
  not the `ollama` selector — noted as an option, not taken. Native `ollama serve` stays supported.
- Caveats written into `application-offline.properties`: CPU-only on macOS; `llama3.1` (8B) wants
  ~6–8 GB on top of the other four containers — bump the Docker VM or drop to `llama3.2:3b`.
- **RAM caveat confirmed empirically**: a later `make up-offline` OOM-killed Cassandra (exit 137,
  `cassandra-init` then fails its `depends_on`) with the `ollama` container also running on the
  Colima VM. Same failure mode [[2026-08-31]] capped Cassandra's heap for; the offline profile eats
  the remaining headroom. Postgres/Qdrant/Kafka were unaffected.
- **Race fix**: the first cut pulled models via an async `ollama-init` sidecar; `up -d` returns
  before the ~5 GB pull finishes, so `make up-offline && make run-offline` raced the app against a
  half-downloaded model (404 on collection sizing). `make up-offline` now pulls **synchronously**
  and blocks; `ollama-init` deleted.
- **Volume**: briefly made `ollama-models` `external` so `make nuke` wouldn't force a re-download,
  then reverted on request — it's a plain compose volume, `make nuke` wipes it, `make up-offline`
  re-pulls (and blocks, so the result is still a working stack).
- **Orphan fix**: deleting the `ollama-init` service left its stopped container behind on `make
  nuke` — `docker compose down` ignores containers whose service is no longer in the file. Added
  `--remove-orphans` to `down` / `nuke` / `up-offline`.
- **"`make run-offline` is stuck" — it wasn't.** `./gradlew bootRun` parks on a
  `EXECUTING [Nm]` progress line for the app's whole lifetime (the task never completes), which
  reads as a hang. Thread dump confirmed: `main` already exited, `/actuator/health` 200, seeded
  login 200. Nothing to fix — suggested `--console=plain` or a `curl` from another terminal.

### Bug found on the first real end-to-end boot: non-UUID Qdrant point id

- `make run-offline` is the **first time the backend has actually booted against a live Qdrant +
  embedding model** on this machine (no AWS creds until now — see [[2026-08-31]]). It immediately
  crashed in `KnowledgeBaseIndexer`: `IllegalArgumentException: Invalid UUID string: order_status`.
- Root cause: `toDocument()` set the Spring AI `Document` id to the raw intent id. Spring AI 2.0.0's
  `QdrantVectorStore.doAdd` runs `UUID.fromString(id)` on every point — Qdrant ids must be uint64 or
  UUID.
- Fix: derive a stable name-based UUID (`UUID.nameUUIDFromBytes(intentId)`). Idempotent re-upsert
  still holds; nothing downstream reads the id — `ChatPipelineService.toCandidateIntents` keys off
  the `topic` metadata, which already carries the intent id. After the fix the app boots and
  `support_kb` seeds (0 → 4 points, 768-dim `nomic-embed-text`). Same bug would have hit the
  staging/prod KB-bootstrap Job. See [[support_kb]], [[rag-pipeline]].

### Chat OOMs on the first turn — Colima VM too small for llama3.1

- Symptom (later session): starting a conversation under `local,offline` throws
  `TransientAiException: HTTP 500 - llama-server process has terminated: exit status 1:
  ggml_aligned_malloc: insufficient memory (attempted to allocate 4402.48 MB)`, at
  `QueryNormalizationService` — RAG stage 1, the first chat-model call. Retried 3× then fails the
  turn.
- Root cause: not code. `colima list` / `docker info` showed the VM at **2 GiB / 2 CPUs**, shared
  with Postgres/Cassandra/Qdrant/Kafka. The containerised Ollama loading `llama3.1` (8B) needs a
  ~4.4 GB CPU weights buffer — can't fit. Host has 32 GiB; the VM was just never sized up. Exactly
  the "RAM caveat confirmed empirically" risk from *Ollama in a container* above, now landing on the
  chat path instead of Cassandra.
- Fix (with user): resize the VM — `colima stop && colima start --cpu 6 --memory 16` (12 GiB
  practical minimum, 16 for slack). No model swap, no app-code change. Rejected alternatives:
  `llama3.2:3b` (weaker at the two structured-output stages), native host `ollama serve` (fastest
  via Metal GPU but then Ollama isn't managed by `make up-offline` / `make nuke`).
- Made the requirement concrete everywhere it was vague ("raise the Docker VM memory"):
  `application-offline.properties` + `local/docker-compose.yml` comment blocks, the `CLAUDE.md`
  `run-offline` bullet, [[running-locally]] (new Prerequisites + Troubleshooting rows), and one
  clause each in [[local-vs-aws]] and [[roadmap]].

### Slot-filling NPE on the second turn of a dialogue — empty Cassandra map reads back null

- Symptom: `NullPointerException: ... "slots" is null` at `SlotFillingService.missingSlots:17`
  (`intent.requiredSlots().stream().filter(slot -> !slots.containsKey(slot))`), reached via
  `ChatPipelineService.continueSlotFilling:142` from `handleMessageStream` / `handleMessage`.
- Root cause: turn 1 persists a `DialogueState{status=SLOT_FILLING, slots=Map.of()}`; Cassandra
  stores an empty `map<text,text>` as *no cell*, so `findById` on turn 2 returns `slots == null`.
  Same gotcha as the `participantIds` note above and `ChatHistory.participantIds`, different field.
  `ChatPipelineServiceTest` mocks `DialogueStateRepository`, so the real round-trip was never
  exercised.
- Two more `state.getSlots()` derefs on the reloaded path would have failed next:
  `ChatPipelineService:146` (`new HashMap<>(null)`) and `:239` → `PromptBuilder:44` (`slots.isEmpty()`).
- Fix: hand-write `DialogueState.getSlots()` to coalesce `null → Map.of()` — Lombok `@Getter` skips a
  field with an existing getter, so one place covers all three derefs and any future caller. Plus a
  defensive `null` guard in `SlotFillingService.missingSlots` (public API taking the map directly).
  No change needed in `ChatPipelineService` / `PromptBuilder`. See [[rag-pipeline]], [[dialogue_state]].
- Tests: `ChatPipelineServiceTest.continuesSlotFillingWhenReloadedStateHasNullSlots` (stubs
  `findById` → `SLOT_FILLING` state with `slots=null`, asserts a clarifying question, not an NPE);
  **new** `SlotFillingServiceTest` (null map → all required slots missing; filled slots excluded in
  declaration order). `./gradlew :server:build` green.
