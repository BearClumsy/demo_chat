# 2026-09-04

## Chat: three visibility bugs found on first real UI use, all fixed

First time the React client was actually driven end-to-end against a live backend surfaced three
separate bugs in the start-chat / streaming-reply path. See [[Chat]].

- **Opening message never got a reply.** `ChatService.startChat` persisted the chat with the first
  message already inlined into `ChatHistory.messages` but never ran it through
  `ChatPipelineService` — so `POST /api/chats` returned only a chat id, no assistant reply, and the
  client's `StartChatForm → ChatWindow` handoff dropped the user's own first message on the floor
  (nothing to render it from). Fix: `startChat` now saves the chat with an **empty** message list,
  then calls `chatPipelineService.handleMessage(...)` and returns a new `StartChatResponse{chatId,
  reply, status}`. `App.tsx` seeds `ChatWindow`'s initial message list from that response (both the
  user's message and the assistant's reply) instead of starting empty.
- **Duplicate assistant bubble under React StrictMode.** `useChatStream`'s stream-`onDone` handler
  appended the final message from inside a `setStreamingReply` state updater — StrictMode
  double-invokes updaters in dev, so the append ran twice. Fix: track the in-flight reply in a
  `useRef` instead of deriving it from the state updater's `prev` argument; the `finally` block reads
  the ref once and appends exactly one message.
- **Garbled reply text.** The SSE frame parser trimmed each `data:` line wholesale
  (`.trim()`), but `TextChunker.chunk()` (server side) deliberately appends a trailing space to every
  word-chunk except the last so tokens concatenate back into readable text — trimming ate exactly the
  separators that made that scheme work. Fix: only strip the single conventional leading space after
  `data:` per the SSE spec, not trailing whitespace.
- New/updated tests: `ChatControllerStartChatTest`, `ChatServiceStartChatTest` now assert the
  `StartChatResponse` shape and that `ChatPipelineService.handleMessage` is invoked with the opening
  message.

## Auth: default the login/signup toggle to login

`AuthPage` initialized `mode` to `"signup"`; flipped the default to `"login"` — signup is the rarer
path once a test user is already seeded locally.

## Tooling: `make stop` to kill a foregrounded local run

`make down` only stops the Docker containers, leaving no way to stop a foregrounded `make
run`/`run-offline` from another terminal. New `make stop` finds whatever process is bound to
`APP_PORT` (default 8080) via `lsof -ti tcp:$(APP_PORT) -sTCP:LISTEN` and kills it — `bootRun` gives
the JVM no distinctive process title to `pgrep` on safely, so port-binding was the reliable signal.
