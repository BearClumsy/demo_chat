# 2026-07-15

## API — RAG pipeline Phase 2
- Implemented the remaining three Phase 2 roadmap items on top of yesterday's Phase 1 pipeline: output-side
  guardrail, semantic cache, SSE streaming (Redis for dialogue state was dropped as out of scope — already
  superseded by Cassandra). Decided the build order deliberately: guardrail before cache, since the cache
  write needed the guardrail's verdict to decide what's cacheable; SSE last, built against the finalized
  `generateAnswer`.
- **Guardrail** ([[rag-pipeline|rag-pipeline.md]]'s `ResponseValidator` + `GroundednessCheck`): a second LLM
  call per answered turn checks the generated text is grounded in the intent's `knowledge_snippet`. A failed
  check swaps the reply for the intent's `escalation_fallback` and sets a new `DialogueStatus.ESCALATED`
  (distinct from `OUT_OF_SCOPE`, which is pre-generation). Reuses the existing `ChatClient` bean rather than
  a separate/cheaper model.
- **Semantic cache** (`SemanticCacheService`, see [[semantic_cache]]): chose a second Qdrant collection over
  a Cassandra exact-match table, so cache hits catch semantically similar repeats, not just literal string
  repeats — reuses the existing `VectorStore`/`SearchRequest` API instead of a hand-rolled embedding lookup.
  Checked right after query normalization, short-circuiting retrieve/classify/generate/guardrail on a hit.
  Writes are gated on the guardrail passing, specifically to avoid caching a hallucinated answer.
- **SSE streaming** (`POST /api/chats/{chatId}/messages/stream`): went with **buffer-then-chunk**, not live
  token-by-token generation via Spring AI's `ChatClient.stream()` (unused anywhere in this codebase). Live
  streaming would mean the guardrail could only run after the client already saw the text — buffer-then-
  chunk keeps the guardrail's full pre-send guarantee at the cost of not being "real" streaming.
- Reused `handleMessage`'s pre-generation stages unchanged for `handleMessageStream` — clarifying-question,
  out-of-scope, and cache-hit paths all go through the SSE endpoint too, as a very short token stream.

## Data layer — R2DBC migration
- Migrated `user/*` (and `ChatService.validateParticipantIds`) from blocking JPA to R2DBC — the one place
  in the app where a real reactive Postgres driver exists (see [[users]]). Bedrock/Qdrant calls in `rag/*`
  deliberately stay on `Schedulers.boundedElastic()` bridging; neither has a reactive-native client in this
  Spring AI version, so that bridging is correct practice, not a gap to close.
- Kept a separate blocking JDBC `DataSource` (`spring-boot-starter-jdbc`) solely for Flyway migrations,
  alongside the new `spring.r2dbc.*` config for the app — the two connection configs point at the same
  database but can't be collapsed into one.
- `ChatService.validateParticipantIds` needed a real rewrite, not a mechanical port: `findAllById` on a
  reactive repository returns `Flux<User>`, so the old blocking-`List` containment check became a
  `Flux.map().collect(toSet()).flatMap()` chain.

## Infrastructure & tooling
- `org.testcontainers:junit-jupiter`/`postgresql` don't exist as artifact coordinates in Testcontainers
  2.0.5 (the version this project's Spring Boot 4.0.7 BOM manages) — they were renamed to
  `testcontainers-junit-jupiter`/`testcontainers-postgresql`. Found by unzipping the actual
  `testcontainers-bom` POM from the Gradle cache rather than guessing.
- `@DataR2dbcTest` isn't in `spring-boot-test-autoconfigure` in this Spring Boot version — Boot 4 split data
  test slices into per-feature artifacts (matching the per-feature `-test` starter convention already used
  in `build.gradle`). Real package: `org.springframework.boot.data.r2dbc.test.autoconfigure.DataR2dbcTest`,
  in the separate `spring-boot-data-r2dbc-test` module.
- Colima + Testcontainers: Ryuk's own container failed to start (`operation not supported` mounting the
  Colima docker socket path) because Colima's daemon runs inside a Lima VM where the host-side socket path
  isn't a real path there. Workaround: `TESTCONTAINERS_RYUK_DISABLED=true` + `DOCKER_HOST` pointed at
  Colima's socket — a Colima-specific quirk, not a project bug, so not baked into the build.
- `@AuthenticationPrincipal` + Spring Security reactive test support behaved inconsistently under
  `@WebFluxTest` + `@SpringBootTest`'s `ReactorContextTestExecutionListener` (a custom `UserPrincipal`
  resolved as a non-null-but-empty-`user` object — never fully root-caused). Sidestepped by binding
  `WebTestClient` directly to the controller (`bindToController`, manually registering
  `AuthenticationPrincipalArgumentResolver` + `SecurityMockServerConfigurers.springSecurity()`) instead of
  going through the full app context slice — simpler and more predictable for a controller-only test anyway.
- Added the project's first Testcontainers dependency and first real test coverage beyond the placeholder
  `contextLoads()`: `UserRepositoryTest` (R2DBC/Testcontainers-Postgres), `ChatServiceValidateParticipantIdsTest`,
  `ResponseValidatorTest`, `SemanticCacheServiceTest`, `ChatPipelineServiceTest`, `TextChunkerTest`,
  `ChatControllerStreamTest`.
