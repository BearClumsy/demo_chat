# Feature: User

**Status:** in progress — read and create implemented; no update/delete/list/auth yet

## Overview

Core user record for the app: identity fields (name, email, login) plus a hashed password. Currently
exposes read-by-id and create; this is the foundation other features (auth, chat ownership, etc.) will
build on.

## Requirements

- A user has: first name, last name, email, phone (optional), login, password.
- Email and login must each be unique.
- Passwords are never stored or returned in plaintext.
- Fetch a single user by id.
- Create a new user from a front-end-submitted payload, with input validation.

## Infrastructure Used

- Postgres: [[users]]

## Decisions

- **UUID primary key**, not auto-increment — avoids leaking sequential/guessable ids through the API.
  Generated by Hibernate (`GenerationType.UUID`) on the Java side, with a DB-level default
  (`gen_random_uuid()`) as a fallback for non-JPA inserts.
- **Package-by-feature** (`com.example.demo_chat.user`) rather than package-by-layer — keeps the
  entity, repository, service, DTOs, and controller together instead of scattered across
  `controller/`, `service/`, `repository/` packages.
- **Password hashing via BCrypt** (`spring-security-crypto`, not the full Spring Security starter, to
  avoid pulling in auth filters that would affect unrelated endpoints).
- **Response DTO (`UserResponse`) deliberately excludes `password`** — the entity is never serialized
  directly.
- **Duplicate email/login → 409 Conflict**, not 500 — caught via `DataIntegrityViolationException`
  against the DB's unique constraints rather than a pre-check (avoids a check-then-insert race).
- Reactive endpoints (WebFlux) sit on top of blocking JPA/JDBC — bridged per-call with
  `Schedulers.boundedElastic()` in `UserService`, since there's no R2DBC driver in this project.

## Open Questions

- No update, delete, or list-users endpoint yet.
- No authentication/login endpoint yet — `password` is stored but nothing currently verifies it.
- Should there be a canonical "username" (login vs email precedence) once auth is built?
