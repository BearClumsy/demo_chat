# Feature: User

**Status:** in progress — create/read implemented and the record now backs app-wide authentication; no
update/delete/list endpoints

## Overview

Core user record for the app: identity fields (name, email, login) plus a hashed password. Exposes
read-by-id and create, and doubles as the credential store for HTTP Basic authentication — every
endpoint except `POST /api/users` and the health probes authenticates against it. Chat ownership and
participant validation resolve against these ids (see [[Chat]]).

## Requirements

- A user has: first name, last name, email, phone (optional), login, password.
- Email and login must each be unique.
- Passwords are never stored or returned in plaintext.
- Fetch a single user by id.
- Create a new user from a front-end-submitted payload, with input validation.
- Authenticate requests against the stored credentials, exposing the user's id to request handlers.

## Decisions

- **UUID primary key**, not auto-increment — avoids leaking sequential/guessable ids through the API.
  Generated by the DB (`gen_random_uuid()` default in `V1__create_users_table.sql`): the R2DBC entity
  leaves `@Id` null on insert, so the column default is what actually assigns the id.
- **Package-by-feature** (`com.example.demo_chat.user`) rather than package-by-layer — keeps the
  entity, repository, service, DTOs, and controller together instead of scattered across
  `controller/`, `service/`, `repository/` packages.
- **Password hashing via BCrypt** (`PasswordEncoderConfig`). The original rationale for depending on
  `spring-security-crypto` alone was to avoid pulling in auth filters; that no longer applies — the full
  `spring-boot-starter-security` is now on the classpath and `SecurityConfig` deliberately configures
  those filters.
- **Response DTO (`UserResponse`) deliberately excludes `password`** — the entity is never serialized
  directly.
- **Duplicate email/login → 409 Conflict**, not 500 — caught via `DataIntegrityViolationException`
  against the DB's unique constraints rather than a pre-check (avoids a check-then-insert race).
- **Fully reactive persistence.** `UserService` and `SecurityUserDetailsService` call the R2DBC
  `UserRepository` directly, with no `Schedulers.boundedElastic()` bridge. Postgres was the one store in
  this project with a reactive-native driver, so it was migrated off JPA/JDBC; blocking JDBC remains on
  the classpath only so Flyway has a `DataSource` for migrations.
- **`login` is the authentication username**, not email — `SecurityUserDetailsService` resolves
  principals via `UserRepository.findByLogin`.
- **`UserPrincipal` exposes `getId()`** on top of `UserDetails` so handlers can use the authenticated
  user's id (`@AuthenticationPrincipal`) without a second lookup — this is what the chat endpoints check
  authorization against.

## Open Questions

- No update, delete, or list-users endpoint yet.
- No login endpoint or session — authentication is HTTP Basic on every request, so the client stores the
  raw credentials in memory and rebuilds the header each call. A page refresh logs the user out.
- Users have no roles or authorities (`UserPrincipal.getAuthorities()` returns an empty list), so there
  is nothing to build role-based authorization on.
- Should email be accepted as an alternative login identifier alongside `login`?
